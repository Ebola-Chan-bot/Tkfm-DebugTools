# 保护机制分析

nProtect AppGuard 是韩国 INCA Internet 的移动应用保护方案，通过 native 层加壳实现代码加密、反调试和完整性校验。天下布魔使用的版本包含以下保护层。

## native 库布局

APK 的 `lib/arm64-v8a/` 目录中包含多个经过 NP 处理的库，各库的保护程度不同。`libil2cpp.so`是 Unity IL2CPP 运行时和游戏代码，其代码段被 NP 加密，ELF 头部只保留 `.dynsym`、`.dynstr`、`.dynamic`、`.shstrtab` 四个节，唯一导出符号为 `SoLibraryStart`。`libcompatible.so`是 NP 主体，负责运行时解密和环境检测。`libstub.so`是引导桩，`DT_INIT` 中调用 `SoLibraryStart` 启动 NP。`libengine.so`不是标准 ELF，而是 NP 的内容容器，存放加密的引擎组件。

## 元数据加密

Unity 的 `global-metadata.dat` 被 NP 加密为 AEI 自定义格式。文件以 3 字节魔术码 `AEI` 开头，头部 31 字节包含输出长度、读取长度、压缩长度和一个 16 字节的加密数据密钥。数据段使用 AES-ECB 分组加密，加密前经过 LZ4 压缩。解密需要两层密钥：静态密钥用于解密头部中的数据密钥，数据密钥用于解密数据段。

## 代码加密

`libil2cpp.so` 的代码段采用 NP 的按需解密机制。运行时由 `libcompatible.so` 的 DT_INIT 解密 IL2CPP 代码段，解密过程涉及大整数模幂运算（RSA 类操作），每次模幂运算通过陷阱指令 `0xfcfdc` 触发。NP 还在运行时动态填充函数指针表（`impls`），注册信号处理器，并在 DT_INIT 结束时对自身代码进行重加密以防止 dump。

# 提取管线详解

管线分为五个阶段，每个阶段的输出作为下一阶段的输入。

## 阶段一：APK 解压

使用 Python `zipfile` 从 APK 中提取关键文件。需要提取 `lib/arm64-v8a/` 下的 `libil2cpp.so`、`libstub.so`、`libcompatible.so`、`libengine.so`，以及 `assets/bin/Data/Managed/Metadata/global-metadata.dat`。

## 阶段二：元数据解密

读取加密的 `global-metadata.dat`，按 AEI 格式解析头部。静态 AES-128 密钥内嵌于 `libcompatible.so` 中，通过扫描 16 字节候选并试解密自动提取（详见下文解密算法一节）。用静态密钥解密头部偏移 15 处的 16 字节数据密钥，再用数据密钥以 AES-ECB 模式解密数据段，最后对解密结果做 LZ4 解压。解密后的元数据以标准 IL2CPP 魔数 `AF 1B B1 FA` 开头，版本号 31（Unity 2022.3.x）。

## 阶段三：方法表解析

解析 IL2CPP 元数据 v31 的表结构。元数据头部 8 字节后是 31 组 `(offset, size)` 对，分别指向字符串表、方法定义表、类型定义表、图像定义表等。方法定义表每条 36 字节，包含名称索引、声明类型、返回类型、参数起始、token、标志位等字段。类型定义表每条 88 字节，包含名称、命名空间、方法起始、方法数量等字段。

## 阶段四：战斗方法识别

识别过程分两层。第一层按类型名模式匹配（人工归纳）定位战斗相关类型，对其声明的全部方法按索引范围**自动收集**——方法名从元数据动态读取，不依赖任何硬编码名称。第二层使用一份人工筛选的关键方法名清单（逆向分析确定的名称），用于给已收集方法添加高亮标记，并补收不在战斗类型中但名称匹配的方法（如 `AI`、`UI_Avg` 等类型下的入口）。结果导出为战斗方法索引表。

## 阶段五：IL2CPP 代码恢复

这是最复杂的阶段，需要通过 Unicorn CPU 模拟运行 NP 的解密逻辑来获取明文代码。核心思路是：在模拟器中加载加密的 `libil2cpp.so` 和 NP 库，执行 NP 的 DT_INIT 解密流程，一次性跑完全部解密后保存完整的内存快照，然后从快照中提取 IL2CPP 代码段并按方法地址反汇编。

反汇编的函数边界按「全部方法入口地址排序」确定：先把 CodeGenModule 方法指针表中的所有入口收集去重并按地址升序排列（本作共 30637 个唯一入口），每个函数的反汇编区域即 `[本方法入口, 下一更高入口)`，这样天然不会越界写入下一个函数。不能用「下一条方法指针表项」推断边界，因为 IL2CPP 方法指针表按元数据定义序排列而非地址序；也不能在首个 `ret` 处停止导出——ARM64 函数常有多个返回点和尾部跳转，首个 `ret` 之后往往仍有真实代码（实测 265 个战斗方法中有 130 个在首个 `ret` 之后还有代码，合计 12133 条指令，旧版截断逻辑会全部丢失）。每个 `.asm` 文件头部带 `; region=<起>-<止>  instructions=N` 审计行，导出后可核对指令数与区域是否吻合。

# 关键技术细节

## AES-ECB + LZ4 解密算法

AEI 格式的解密分为三步。第一步，获取静态密钥——该密钥内嵌于 `libcompatible.so` 的二进制中，通过扫描 16 字节候选密钥并试解密验证自动提取：对每个候选，先用 AES-ECB 解密头部中的加密数据密钥，再对解密结果做 LZ4 令牌结构快速过滤（首块字面量必须包含 IL2CPP 魔数），最后完整解密验证。第二步，用数据密钥以 AES-ECB 解密数据段。第三步，对解密结果做 LZ4 块解压。注意此处是 AES-ECB 而非 AES-CBC，无 IV，两层均为 ECB 模式。

## Unicorn 模拟 NP 解包

使用 Unicorn Engine 模拟 ARM64 执行 NP 的解密流程。

模拟前先向 NP 函数表（`impls`）写入真实实现地址（`0x1b2be8`→`0x132d24` 等 5 项），使模幂运算和字符串解密能正常执行。同时注册模幂陷阱钩子——在地址 `0xfcfdc` 捕获模幂运算入口，将参数传递给真实模幂实现（`0x82c58`）执行后继续。

## 模幂运算恢复

NP 的大整数模幂运算是 IL2CPP 代码解密的核心操作。运算以 65536 为基（每槽 16 位），包含乘法（`0x82574`）、模约简（`0x82c58`）和回写三个步骤。陷阱指令位于 `0xfcfdc`，其前一条伪指令破坏了 `x1` 寄存器（模数指针），需要从 `x20` 恢复。模幂结果写入栈上隐藏返回对象（`sp+8`）。通过 Unicorn 钩子拦截陷阱、调用真实模幂实现、将结果写回内存，可以正确模拟这一过程。
